## Fixed this session

### A1 - CLI reads the wrong site's settings row (CRITICAL) - VERIFIED HERE
`goodsreceived:recompute_active_from_stock` activated 95 offers and deactivated ZERO on .no,
despite site 1 settings carrying `auto_deactivate_on_zero: 1`.

Chain: `SettingsAccessor` -> `Settings::get()` -> `SettingModel::instance()` ->
`getSettingsRecord()` -> `MultisiteScope` -> `Site::getSiteIdFromContext()`. Outside an HTTP
request `App::runningInBackend()` is false and `system.active_site` is never set (only HTTP
middleware sets it), so it falls through to `getPrimarySite()`. On .no the primary site is
site 2, the DISABLED "Latvian (source)" site, whose row is
`{"enabled":true,"auto_activate_on_stock":true}` - no `auto_deactivate_on_zero` key at all.
Missing key -> `Settings::get()` returns null -> `(bool) null === false`. The deactivate branch
in `decideTargetState()` is dead; the activate branch fires. Hence 95/0.

The `!$bAutoDeactivate && !$bAutoActivate` early return did NOT trigger, which is why the run
looked successful.

**StoreExtender's `SettingsSiteFallbackHandler` cannot fix this** - verified at
`modules/system/models/SettingModel.php:106-111`: `instance()` fires `model.initSettingsData`
only when `getSettingsRecord()` returns null. Site 2 HAS a row (a partial one), so the hook
never fires. Adding this plugin's Settings to `AR_SETTINGS_MODEL_LIST` would be a no-op.

Fix applied: `--site=` option wrapping `handle()` in `Site::withContext()`, plus the command now
PRINTS the resolved site id and both toggle values before doing anything. A run against the
wrong row was previously indistinguishable from a correct one.

Recovery invocation for .no: `--site=1`.

### A2 - CLI never invalidates any cache (CRITICAL) - VERIFIED HERE
`ActiveFlagService` writes via `saveQuietly()` and its docblock states cache flushing is the
caller's job. On the invoice path that caller is `ApplyOrchestrator` (`flushAffectedCaches()`
post-commit). The CLI had no equivalent and called nothing. Net effect on .no: the command's
work was invisible on the storefront - stale `OfferActiveListStore`, `ProductActiveListStore`
and per-id `OfferItem` (which caches both `active` and `quantity`).

Fix applied: the command now calls `StockApplyService::flushAffectedCaches()`.

### A3 - `reconcileAll()` never reactivates parent products (HIGH) - VERIFIED HERE
`reconcile()` (invoice path) collects activated product ids and calls
`reactivateInactiveProducts()`. `reconcileAll()` (CLI path) called `reconcileSingleOffer()`
directly and never collected them, so `reactivateInactiveProducts()` was unreachable from CLI.

This is the .no recovery workflow exactly: reset deactivates every product, stock returns,
offers flip active, every parent product stays inactive, `ProductActiveListStore` keeps the
catalog empty. Products needed a separate manual UPDATE on .no.

Fix applied: new `reconcileAllDetailed()` returns `{offers, products}` and performs the
reactivation; `reconcileAll()` is now a thin count wrapper (signature unchanged).
Also folded in the `ProductItem::clearCache()` gap (F14a below) for this path, since
`reactivateInactiveProducts()` writes via a mass UPDATE that fires no model events.

## Open - parser/matcher layer

| # | Sev | Finding |
|---|-----|---------|
| F1 | **CRITICAL** | `VariationMatcher` writes stock to the WRONG OFFER. MySQL matches `whereIn('variation', ...)` case/accent-insensitively (`utf8mb4_unicode_ci`); PHP then re-keys byte-exactly, so the single-offer ambiguity guard only ever sees one case-bucket. Real data: `variation IN ('BLACK')` returns 13 rows (twelve `Black`, one `BLACK`) - a line reading `BLACK` matches the lone id and passes the guard. Inverse case: `FAIRY PEARL` vs stored `Fairy Pearl` produces a false "unmatched". 11 variation groups collide this way. Invisible in tests: SQLite `whereIn` is BINARY, and every variation fixture uses numeric tokens. |
| F2 | HIGH | Real goods lines are dropped before matching. Any col-2 cell that is not exactly 13 digits is discarded as `invalid_ean` - but in the real fixtures those are 8-digit internal article codes and empty EAN cells carrying genuine stock. ~14 of 149 lines (~9%) on one sample invoice. Aggravating: only 1403 of 6703 offers have a 13-digit numeric `code`. |
| F3 | HIGH | Those dropped rows are invisible to the operator. `skipped_rows` is write-only (one `count()` in a log line); `total_lines` is set to the POST-skip count, so a 149-line delivery note displays as a complete 135-line invoice and every number reconciles. |
| F4 | MED/HIGH | The one strategy that could rescue them (`VariationMatcher`, name-based, needs no EAN) is structurally unreachable - the parser drops the row first, and `assertAllEansValid()` would abort the whole invoice anyway. |
| F5 | MED | Same double-override / unique-violation leak as A10 (same root, reported by both audits). |
| F6 | MED | `row_index` is not the invoice's line number - it counts every XPath-matched row including headers, and burns an index on each skip. Off by one on the LV template, gapped on all. It is the operator's only cross-reference to the paper document. |
| F7 | MED | Same DB-keyed-map / input-keyed-lookup collation trap in `OfferCodeMatcher` and `ProductCodeSingleOfferMatcher`. Not firing today (no padded codes in the DB) but latent. |
| F8 | MED | `ProductCodeSingleOfferMatcher` requires EXACTLY one offer; any product with 2+ offers is rejected with no disambiguation. The fallback then needs a globally unique variation, and 562 variation values are shared - which is why `variation` matched 1 line out of 633. |
| F9-F18 | LOW | XPath `contains('R20')` would sweep `R200`; a stale doc comment about shared column positions; `trim()` misses U+00A0 (one nbsp in a qty cell aborts the entire upload); `PriceNormalizer` blanks on thousands separators; `ltrim` charlist vs prefix; silent `MAX_ROWS` truncation; byte-based `substr` can split UTF-8 in `skipped_rows.raw`; a filename date typo blanks the country code; no `MATCH_STRATEGY_VARIATION` constant (literal hardcoded in 3 places); `reorderToInput` can silently shrink output on duplicate `row_index`. |

### Why 7 of 633 lines were unmatched
Ranked: EAN genuinely absent from both `offers.code` and `products.code` (correct outcome,
likely most of them); product has 2+ offers so F8 rejects and F1/F8 block the fallback;
F1 case mismatch; soft-deleted offer excluded by global scope.
Not causes: leading zeros, check digits, BOM/CRLF - all handled and pinned.

The framing worth pushing back on: 7 unmatched rows is the visible tail. F2 is the invisible one.

## Test gaps that let these through
1. Collation semantics (F1, F7) - all matcher tests run SQLite/BINARY. The critical bug is
   invisible by construction. Needs a MySQL-backed test.
2. `HtmInvoiceParserTest.php:152-157` **pins the data loss as correct** - asserts 135 lines and
   names `40092454` as an expected skip. Any F2 fix must rewrite that assertion first.
3. No test asserts `skipped_rows` is surfaced anywhere.
4. `row_index` is never compared against the document's own line number.
5. Double override -> unique violation untested (the only override test uses a spy).
6. No test covers a multi-offer product rescuable by name.
7. Soft-deleted offer/product exclusion untested.

## Explicitly correct - do NOT "fix"
`chunkById` while mutating the filter column (the value stays `!= 'operator'`);
`!= 'operator'` vs SQL NULL (column is NOT NULL DEFAULT 'system');
`lockForUpdate()` inside `DB::transaction`; `flushAffectedCaches` outside the transaction
closure; `InvoiceLine::insert()` bypassing model events; `offers_touched` counting unique
offers; `Offer` not being site-filtered (it links to sites via a pivot, not a `site_id` column);
`--chunk` coercion; `onApplyBulk`'s status filter.
